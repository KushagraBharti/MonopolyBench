# Downstream Full-Game-to-Fixture Bridge Contracts

Status: pre-pilot contract  
Contract date: 2026-07-29

These contracts create research artifacts downstream of the benchmark. They must not
change engine rules, prompts, tools, memory limits, retries, fallbacks, or actions in
the source game.

## 1. Evidence levels

Every bridge output declares one of four levels:

1. **Observed:** bytes or records directly preserved in a canonical run.
2. **Deterministic derived:** a reproducible transformation of observed artifacts.
3. **Bounded branch:** a legal alternative evaluated for one declared engine step.
4. **Interpretive:** a human or judge label with evidence and uncertainty.

No level may be silently promoted to another.

## 2. Trajectory fixture extraction contract

### 2.1 Selection

A fixture-selection manifest is frozen before extracting confirmatory fixtures. It
contains:

```json
{
  "fixture_selection_version": "trajectory_fixture_selection_v1",
  "source_campaign_id": "string",
  "source_partition": "pilot|confirmatory_discovery|confirmatory_heldout",
  "selection_seed": 0,
  "selection_rule_hash": "sha256",
  "eligible_decision_types": ["string"],
  "strata": [{"stratum_id": "string", "target_count": 0}],
  "exclusions": [{"reason_code": "string"}]
}
```

Selection may use deterministic state and event attributes such as decision type,
shortfall, legal-action count, monopoly completion, auction depth, trade depth, house
scarcity, or rent shock. It may not inspect model identity, final winner, private
thought content, or human behavioral labels unless that dependency is an explicitly
named exploratory stratum.

### 2.4 Extraction procedure

1. Verify source inventory and source-run hashes.
2. Load run config, players, actions, events, decisions, and prompt artifacts.
3. Initialize the engine with the exact source seed and config.
4. Replay the action prefix to the target decision, asserting every decision ID.
5. Update a fresh `PromptMemory` with every replayed event in source order.
6. Stop before applying the target action.
7. Persist order-preserving, compact JSON copies of the decision and prompt memory.
   Sorted/indented copies are human-readable companions only: JSON key order is
   semantically irrelevant to the engine but changes serialized prompt bytes.
8. Regenerate the decision, prompt, and tools using the original system prompt,
   order-preserving inputs, and source player configuration.
9. Compare original and regenerated bytes.
10. Independently rebuild memory from the recorded event prefix and compare again.
11. Freeze the fixture only if the declared integrity gate passes.

### 2.5 Extraction acceptance

An `exact_history` fixture requires:

- identical decision ID, type, actor, turn, state, and legal-action menu;
- byte-identical original/regenerated user JSON and tools JSON;
- byte-identical system prompt, or an explicitly allowed newline-only difference with
  both byte and normalized hashes;
- identical engine-replay and recorded-event memory snapshots;
- ordered decision and memory inputs that independently regenerate those exact bytes
  after a write/read cycle;
- all source citations resolving to real artifacts;
- source run files unchanged after extraction.

A mismatch is preserved with a failure code; it is not manually edited into agreement.

## 3. Exact-history replay contract

Exact-history replay means a new model call receives the exact source system message,
user payload, and tool list. It does not mean resuming a provider-side conversation.

### 3.1 Modes

- `source_exact_bytes`: submit the original saved system/user/tools bytes.
- `regenerated_exact_history`: submit regenerated bytes only after byte equality passes.
- `empty_memory_control`: same reconstructed decision but a fresh empty
  `PromptMemory`; diagnostic only.

No other context ablation is supported by this protocol without a separately frozen
prompt-condition experiment.

### 3.2 Invariants

Across exact-history repetitions:

- economic state is identical;
- legal actions and their order are identical;
- system/user/tool bytes are identical;
- model ID, provider route, and reasoning setting are fixed;
- research metadata, source action, score, winner, and human labels are absent;
- each repetition is an independent provider call with a unique call ID.

Before execution, `scripts/research/run_fixture_repetitions.py` must reconstruct every
unique fixture/model prompt variant from the order-preserving inputs and compare its
system, user, and tool SHA-256 values to the frozen source values. Paid execution is
fail-closed unless that gate, the endpoint/route preflight, its freshness limit, the
credit gate, and an exact cost-budget acknowledgement all pass. The default mode is a
zero-call validation.

The repetition manifest is created before any diagnostic provider call.

```json

  "experiment_id": "string",
  "source_fixture_manifest_sha256": "sha256",
  "models": [
    {
      "model_id": "string",
      "provider_constraint": {},
      "reasoning": {},
      "sampling_policy": "provider_default"
    }
  ],
  "repetitions_per_model_fixture": 3,
  "execution_order_seed": 0,
  "calls": [
    {
      "repetition_id": "string",
      "execution_rank": 0,
      "fixture_id": "string",
      "model_id": "string",
      "repetition_index": 0,
      "prompt_mode": "source_exact_bytes",
      "status": "planned"
    }
  ]
}
```

Rules:

- randomize call order across model, fixture, and repetition;
- do not run all calls for one model consecutively;
- preserve failures as results;
- do not selectively repeat surprising or invalid actions;
- a general technical-rerun rule must retain original and rerun records;
- score and branch evaluation occur only after the call ledger is frozen.

## 5. One-step branch contract

### 5.1 Scope

For a fixture decision \(d\) with legal set \(A_d\), replay the exact source action
prefix once for every \(a \in A_d\), apply \(a\), and observe only the immediate engine
transition:

\[
B_1(d,a)=(E_{d,a},s'_{d,a}).
\]

This is exact one-step accounting under the source engine. It is not a prediction of
eventual winner or long-run utility.

### 5.2 Action enumeration

- Start from engine-emitted legal actions only.
- For parameterized actions, enumerate a frozen finite candidate set with a declared
  generator and hash.
- Always include the original applied action.
- Reject candidates that fail the engine's own validator.
- Never invent a semantically attractive action outside the legal schema.

### 5.3 Branch randomness

The branch ends after the target action and immediate automatic consequences. No new
model call occurs. If an action itself consumes engine randomness, the source engine
seed and prefix are identical, and the consumption is recorded. Cross-action
comparisons are described as action-conditioned immediate transitions, not coupled
long-horizon worlds.

### 5.4 Branch outputs

```json
{
  "schema_version": "one_step_branch_result_v1",
  "fixture_id": "string",
  "branch_id": "string",
  "candidate_generator_version": "string",

  "engine_valid": true,
  "validation_errors": [],
  "pre_state_sha256": "sha256",
  "post_state_sha256": "sha256",
  "events_sha256": "sha256",
  "event_ids": ["string"],
  "cash_delta_by_player": {},
  "ownership_delta": [],
  "mortgage_delta": [],
  "building_delta": [],
  "bankruptcy_delta": [],
  "obligation_status": "paid|still_due|bankrupt|not_applicable",
  "source_action": false
}
```

### 5.5 Permitted derived comparisons

- immediate cash retained/raised;
- shortfall closed;
- assets mortgaged or buildings sold;
- monopoly/development change;
- creditor transfer;
- immediate bankruptcy avoided or declared;
- legality and serialization.

Forbidden without a continuation oracle:

- eventual win probability;
- total game value;
- globally optimal action;
- avoidable eventual bankruptcy;
- causal trade surplus;
- winner's curse.

## 6. Provenance requirements

Every fixture/repetition/branch package records:

- source run commit and run-config hash;
- source saved-game manifest and tree hash;
- hashes of actions, events, decisions, states, and prompt artifacts used;
- extraction, replay, and branch script hashes;
- current analysis commit;
- environment/package lock hash;
- selection and repetition manifest hashes;
- provider endpoint snapshot and pricing snapshot hashes;
- generated-output hashes.

Canonical source run directories are read-only. A verifier hashes them before and after
the bridge operation and fails if any byte changes.

## 7. Failure taxonomy

- `SOURCE_HASH_MISMATCH`
- `MISSING_SOURCE_ARTIFACT`
- `DECISION_ID_MISMATCH`
- `STATE_REPLAY_FAILED`
- `RECORDED_EVENT_MEMORY_MISMATCH`
- `PROMPT_SYSTEM_MISMATCH`
- `PROMPT_USER_MISMATCH`
- `PROMPT_TOOLS_MISMATCH`
- `ILLEGAL_BRANCH_CANDIDATE`
- `PROVIDER_ROUTE_MISMATCH`
- `ENDPOINT_ID_MISMATCH`
- `REPETITION_MANIFEST_VIOLATION`
- `USAGE_MISSING`
- `COST_MISSING`
- `GENERATED_HASH_MISMATCH`

Failures remain machine-readable and are included in denominators appropriate to their
stage.

## 8. Quality gates

Before diagnostic results can support a claim:

1. All selected source hashes verify before and after extraction.
2. Every `exact_history` fixture passes byte equality.
3. Every repetition is present exactly once in the result ledger.
4. Every request hash matches its manifest prompt mode.
5. Every parsed action resolves against the fixture legal menu.
6. Every one-step branch begins from the same pre-state hash.
7. Every source citation resolves.
8. All JSON/JSONL/CSV artifacts parse and all hashes verify.
9. Failures and missing usage/cost records are explicitly counted.
10. No research label or source outcome entered a model-facing request.
